## 1. Resumo

- **O que é o Fable:** modelo da Anthropic bloqueado pelo governo americano, reaberto por poucos dias (janela até 07/07, só **50% do limite semanal**). Foi **nerfado** (recusa mexer em segurança/harness), mas segue **superior em abstração e visão sistêmica** — o único que entende *como as peças do sistema se conectam e o que melhorar*. Depois fica caríssimo.
- **Fable ≠ os executores.** Codex, Composer (Grok) e Opus executam código muito bem, mas falham na visão arquitetural. **Opus 4.8 piorou** (segundo ele) pra COP e código. Fable é arquiteto, não pedreiro.
- **Promptar Fable é o oposto do normal:** prompt **aberto e abstrato**. Você aponta uma **dor/problema**, não um passo-a-passo. Analogia: estagiário (diz tudo) vs diretor (aponta o problema e deixa livre). Rigidez no prompt = qualidade despenca.
- **Uso #1 (o de maior valor): otimizar o HARNESS, não o código.** Peça pro Fable refatorar CLAUDE.md, skills, rules, hooks — **reduzindo tokens sem perder função**. Caso real dele: CLAUDE.md de **90k → 37k tokens** com um prompt simples, zero perda.
- **Contra-intuitivo (o insight da aula): quanto melhor o modelo, MENOS harness ele precisa.** Muito harness num modelo bom = gasta mais token e performa PIOR. Ele chegou a **mover skills pra fora e deletar CLAUDE.md** num projeto — ficou melhor. "Modelo que abstrai bem precisa de liberdade" (contratar Steve Jobs e enchê-lo de regra é desperdício).
- **Regra de método: otimize PARA o modelo que fica, não pro Fable.** Fable some dia 7. Não use skills *com* o Fable — peça pro Fable **otimizar suas skills**, depois use-as com Opus/Sonnet/Codex. Ele adapta a skill às peculiaridades de cada CLI (Claude tem subagents/things/workflows/loop; Codex e Composer não).
- **Config prática:** Effort **X-High** (não Max, não Ultra — torram token). **Nunca `/loop` nem ultra-code com Fable** (relê tudo a cada ciclo). **Nunca via API** — sempre assinatura (API dele custou R$400/€110 em minutos). Como só há 50% da cota, **não gaste Fable em código simples**.
- **Workflow híbrido (o uso #1 dele hoje):** **Fable = arquiteto** (cria épicos/ADRs/docs de arquitetura + decisões) → **Codex = orquestrador** (a API da Anthropic cai muito) → **Composer/Grok = executor** de código (rápido/barato). O orquestrador chama o Fable via CLI só quando precisa de decisão arquitetural. Ele executou **8–9 dias** só com a documentação que o Fable criou em 3 dias. **Se você só tem Claude Code:** Fable orquestra + **subagentes Sonnet 5** executam (não precisa de Opus — "Fable aponta o parafuso, o Sonnet aperta").
- **Outros usos fortes:** refatoração/migração de código legado (pega gargalos futuros); **COP/copy** (anúncios, VSL, carta, sequência de e-mail — simula objeções do leitor); interconexão/análise de banco de dados → relatórios que vendem; roteiro de vídeo (fala + cenas); landing pages. E **extrair suas heurísticas** das conversas salvas do Claude Code (como você decide) → virar hooks/rules. Ele tem 200+; o Fable cria *meta-heurísticas*.

## 2. Delta de aplicação — o que muda pro MEU sistema

**O ponto que ninguém mais tem: o Alan é a fonte do meu próprio harness.** Na transcrição ele diz, com todas as letras, que usa o **IoX (AIOX) como harness dele** e que *"em breve tenho utilizado o Fable para otimizar o harness do IoX"*. Ou seja: a otimização que ele prega é **exatamente sobre o framework que eu opero todo dia.** Isso não é uma aula genérica — é o manual de manutenção do meu carro.

E eu **sou o caso clássico do anti-padrão dele.** Meu boot carrega:

| Peça do harness | Tokens (est.) |
|---|---|
| `.claude/CLAUDE.md` | ~3.260 |
| 10 arquivos em `.claude/rules/` | ~8.640 |
| **Subtotal CLAUDE.md + rules** | **~11.900** |
| + skills (WebDesign 10 agentes, clones, 12 agentes AIOX) | acresce muito |

O Alan cortou o dele pela metade e não perdeu nada. Meu CLAUDE.md tem seções que quase nunca são acionadas (graph dashboard, code-intel, tabelas longas) — gordura clássica.

| A aula ensina | Onde eu estou |
|---|---|
| Otimizar harness com Fable (uso #1) | Meu AIOX é justo o harness que ele cita — aplicação direta |
| Quanto melhor o modelo, menos harness | Meu CLAUDE.md+rules ~12k tokens no boot, com gordura |
| Otimizar PARA o modelo que fica (Opus/Sonnet) | Eu rodo Claude Code (Opus 4.8) — é pra ESSE que devo enxugar |
| Fable = arquiteto → Sonnet executa | Combo "Fable arquiteta, subagente Sonnet executa" cabe no meu Claude Code |
| Extrair heurísticas das conversas salvas | Eu já tenho MEMORY.md + memórias de feedback — mesma ideia, subaproveitada |
| Prompt aberto/dor, não passo-a-passo | Bate com meu jeito ("decidir+executar, não menu") |

**Sinais reais (novo/acionável):**
1. 🎯 **Enxugar o harness AIOX é o build de maior alavancagem da semana** — acelera *todos* os outros (CRM, landings, clones, squad). O Alan diz literalmente: é a **primeira** coisa a fazer na janela.
2. 🧭 **"Otimize pro modelo que fica"** — se eu tocar isso com Fable, o alvo é Opus/Sonnet no Claude Code, não o Fable.
3. 🔁 O combo **Fable-arquiteta / Sonnet-executa** é aplicável ao Epic 3 / integração Viziom (arquitetura pesada, execução barata).
4. 🧠 Heurística dele **"reutilizar → adaptar → criar"** é *idêntica* ao meu princípio de não-recriar — reforça que devo formalizar isso como hook.

**Ruído pra mim agora:** as demos de carrinho batendo / jogos 3D / vídeo, a novela Anthropic-vs-Dario, Grok/X como radar de tendência, os prompts que ele mandaria na newsletter. Nada disso aterrissa num build meu hoje.

**Pré-condição que muda a urgência:** tudo acima só é "fazer HOJE" **se eu tiver acesso ao Fable nesta janela (até 07/07)**. Sem acesso, o aprendizado vira **princípio de harness** (enxugar mesmo com Opus) + referência guardada pro retorno do Fable/sucessor.
